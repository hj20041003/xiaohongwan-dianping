# 小红碗点评 · 项目介绍（面试版）

> 用法：① 面试自我介绍时的 30 秒项目陈述 ② 详细架构讲解话术 ③ 技术亮点与难点速查

---

## 一、30 秒电梯陈述（背下来）

> 我做了一个叫「小红碗点评」的本地生活点评平台，类似大众点评+小红书的结合。技术上采用 **Spring Cloud 微服务架构**：按业务领域拆分为用户、商户、笔记、优惠券四个服务，使用 **Nacos 做注册中心、Gateway 做统一入口、OpenFeign 做服务间调用**；数据层用 Redis 承担会话管理、Feed 推送和点赞去重，H2 内库支撑业务数据。前端是 Vue2 + Element UI，实现了验证码登录、探店笔记发布与评论、消息通知、三维评分、地图找店（Leaflet）、优惠券秒杀，以及一个带口令门和地图选点的管理后台。

## 二、架构讲解（面试官追问"讲讲架构"时用）

### 2.1 请求链路

```
浏览器 → nginx:8080（静态资源 + /api 反向代理）
        → Gateway:8090（按路径路由到下游服务）
            ├→ hmdp-user    用户/登录/头像/资料
            ├→ hmdp-shop    商户/分类/评分/收藏
            ├→ hmdp-voucher 优惠券/秒杀券
            └→ hmdp-blog    笔记/评论/消息/关注
服务发现：Nacos ｜ 服务间调用：OpenFeign（blog → user）
```

### 2.2 为什么拆成这四个服务（高频追问）

- **按业务领域/限界上下文拆分**：用户身份、商户资产、内容社区、营销交易，变更频率和数据模型都不同
- **拆分粒度适中**：没有过度拆分（比如没有把"消息"单独拆服务），因为消息强依赖笔记数据，进程内调用更简单可靠——**面试加分点：说明"微服务不是越细越好"**
- 每个服务独立数据库（Database per Service 模式），避免跨库 join

### 2.3 技术选型理由

| 选型 | 理由 |
|---|---|
| Nacos | 注册中心+配置中心二合一，国内生态成熟，支持 AP/CP 切换 |
| Gateway | Spring 官方响应式网关，与 Cloud 生态无缝集成，过滤器体系适合统一鉴权扩展 |
| OpenFeign | 声明式 HTTP 客户端，blog 服务查作者信息只需定义接口 |
| H2（演示环境） | 零安装、启动即建表灌数据，MySQL 兼容模式保证 SQL 可平滑迁移到 MySQL |
| Redis | 会话 Token、Feed 推送（ZSet）、点赞去重（ZSet）、验证码（String+TTL） |

## 三、技术亮点（主动抛给面试官的点）

### 亮点 1：微服务登录态方案
网关不做鉴权，改为 **Token 存 Redis + 各服务拦截器还原用户**：登录服务写入 `login:token:{token}`，下游服务通过拦截器读 Redis 还原 UserHolder（ThreadLocal）。好处：**无状态水平扩展**，任意服务实例都能验证身份。

### 亮点 2：跨服务数据聚合
笔记列表需要显示作者昵称/头像，但用户数据在 user 服务。用 **OpenFeign 批量接口**（/user/batch）一次性取回，避免 N+1 次远程调用——**面试加分点：主动提 N+1 问题及批量优化**。

### 亮点 3：事件驱动的消息通知
点赞/评论笔记后，通过进程内事件写入 `tb_message` 通知作者，未读数用 Redis 辅助统计。点赞用 **Redis ZSet 记录点赞人+时间戳**，天然去重，支持"是否点赞"O(1) 判断。

### 亮点 4：地图找店零成本方案
用 Leaflet + 高德瓦片 + 商户 GCJ-02 坐标，**不需要申请任何地图 Key**；距离排序用经纬度平面近似公式在 SQL 层完成。

### 亮点 5：管理后台效率化
商户新增内置 **Leaflet 地图点选**（点击取经纬度，可拖拽微调）+ 图片上传落盘 nginx 静态目录，运营录店零门槛。

## 四、难点与解决（面试官问"遇到过什么难题"）

| 难点 | 现象 | 排查 | 解决 |
|---|---|---|---|
| 网关转发 500 | 仅用户接口超时 | Nacos 实例列表显示 IP 为虚拟网卡 | 显式指定 `discovery.ip=127.0.0.1` |
| Nacos 客户端连不上 | "Client not connected" | SA 2.2.7 自带 gRPC 客户端 | 服务端升级到 Nacos 2.x（gRPC 端口 9848） |
| 页面"无法输入" | 输入框不渲染 | node --check 发现 JS 语法错误（漏逗号） | 全站脚本语法体检脚本化 |
| 分类页返回全部数据 | 分类过滤失效 | 日志发现 URL 参数混淆（name 双语义） | 分离 search/name 两种模式 |
| 无图笔记导致列表崩溃 | 列表不渲染 | images 为 null 时 split 抛 NPE | 后端默认值兜底 + 前端全链路判空 |

**讲法模板**：现象 → 怎么定位（日志/抓包/对比实验）→ 根因 → 方案 → 沉淀（脚本/规范）。

## 五、可优化方向（面试官问"项目有什么不足"）

1. H2 内存库 → 迁移 MySQL 持久化 + 读写分离
2. 网关接入统一鉴权过滤器（JWT），各服务去掉拦截器
3. 消息通知改用 MQ（RabbitMQ/Kafka）异步解耦，削峰
4. 秒杀补全：Redis 预扣库存 + Lua 原子扣减 + MQ 异步落库（一人一单）
5. 前端工程化：迁移 Vite + Vue3 + TS，组件化重构
6. 接入 Sentinel 熔断限流、SkyWalk 链路追踪
